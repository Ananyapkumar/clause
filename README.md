# Clause — lighting datasheet extraction

Extracts nine structured fields from lighting product datasheets, with an
evaluation harness that measures whether the extraction is actually correct.

**Live:** https://clause-9kq9.onrender.com/docs
*Free tier — the first request after ~15 minutes idle takes about 50 seconds to wake.*

| | v0 |
|---|---|
| Field accuracy | **100%** (27/27) |
| Fully correct documents | **100%** (3/3) |
| Documents in eval set | 3 (1 hard, 2 baseline) |
| Cost per document | $0.00044 |
| Median latency | 40.8 s ⚠️ *see Known Issues* |

Accuracy is measured against ground truth written by hand by someone who works
in the lighting industry — not generated by a model.

---

## The problem

A lighting datasheet states a product's electrical and photometric performance.
Specifiers, wholesalers and contractors pull those figures out by hand, one PDF
at a time, to build quotation schedules and compare products.

The task looks like simple transcription. It isn't, because datasheets
routinely print **several numbers that could plausibly answer the same
question**:

- **System wattage** (total draw including driver losses) and **LED load**
  (the module alone) both appear, often within two lines of each other
- **Efficacy** in lm/W sits next to both wattage and lumen output, and looks
  like it belongs to one of them
- **Warranty hours** are frequently printed more prominently than **L80/B10
  rated life**, and the two differ by a factor of two or more
- **Luminaire flux** (light leaving the fitting) and **LED module flux** (light
  produced before optical losses) are both quoted

Picking the wrong one is not a rounding error. Specify LED load instead of
system wattage and the circuit is undersized. Quote warranty hours as rated
life and the maintenance schedule is wrong.

**Knowing which figure is correct is domain knowledge, not a parsing problem.**

## Who would pay for this

Lighting wholesalers and specifiers processing supplier datasheets into
quotation systems; manufacturers normalising competitor data; anyone
maintaining a product database sourced from hundreds of PDFs in a hundred
different layouts.

## Why AI rather than a parser

Every manufacturer formats differently. There is no consistent label, ordering,
or table structure. A rules-based parser needs a new rule per supplier and
breaks whenever a template changes. A language model reads the document the way
a person does — which is why the disambiguation problem above is the real work,
not the parsing.

## The nine fields

| Field | Type | Notes |
|---|---|---|
| `model_number` | string | Full order code where present, else the model name |
| `wattage_w` | number | **System** wattage, including driver losses |
| `luminous_flux_lm` | number | **Luminaire** output, not bare LED module output |
| `cct_k` | number | Correlated colour temperature, kelvin |
| `cri` | number | Colour rendering index |
| `beam_angle_deg` | number | Degrees |
| `ip_rating` | string | Code as printed, e.g. `IP65` |
| `lifespan_hours` | number | **L80/B10 rated life**, not warranty |
| `dimmable` | boolean | `null` if the document does not mention it |

Conventions: numbers bare, no units, no thousands separators. Units live in the
field name. Absent values are `null` — never `"N/A"` or an empty string.

## Schema decisions

These are the judgement calls. They are documented in `schema.py`, stated
verbatim in the extraction prompt, and applied identically in the ground truth.
They are the difference between a working extractor and a plausible-looking one.

| Decision | Rule | Why |
|---|---|---|
| `wattage_w` | System, not LED load | System wattage is what the circuit must carry |
| `luminous_flux_lm` | Luminaire, not module | Module flux ignores optical losses; it is not what reaches the space |
| `lifespan_hours` | L80/B10 rated life, not warranty | Warranty is a commercial term; rated life is a performance figure |
| `model_number` | Order code preferred over model name | The order code is what gets purchased |

**Deliberately deferred:** `dimming_protocol` (DALI / 0-10V / TRIAC). Adding a
field mid-cycle invalidates every ground-truth file already written and breaks
version comparison. It is scheduled for a version boundary, not a convenient
moment.

## Architecture

```
    datasheet text
          │
          ▼
    ┌──────────────┐        ┌────────────┐
    │  extract.py  │◄───────│ schema.py  │  9 fields + domain rules
    │              │        └────────────┘
    │  · prompt carries the disambiguation rules
    │  · Gemini structured output (native JSON schema)
    │  · Pydantic validation
    │  · retry ×3, feeding the validation error back
    │  · times, counts tokens, computes cost
    └──────┬───────┘
           │
           ├──────────────► requests.jsonl   every call: latency, tokens, cost
           │
           ├──────────────► api.py           POST /extract · GET /health
           │
           ▼
    ┌──────────────┐        ┌───────────────────────┐
    │ evaluate.py  │◄───────│ evals/ground_truth/   │  hand-written
    └──────┬───────┘        └───────────────────────┘
           │
           ▼
    results/v0.jsonl · results/failures.json
```

**Stack:** Python · Pydantic · FastAPI · Google Gemini · Docker · Render

## Evaluation methodology

**Ground truth is written by hand, by a domain expert, and never by a model.**

If the documents and their answers both came from a language model, the score
would measure agreement between two models rather than correctness. The harness
enforces this structurally: every blank ground-truth file starts as
`"FILL_ME_IN"` on all nine fields, and `evaluate.py` refuses to score any case
that still contains a placeholder, a missing key, or an unrecognised key.

**Scoring is strict.** A datasheet value is right or it is not; there is no
"nearly 4940 lumens". The only tolerance is case and surrounding whitespace on
the two text fields. Numeric comparison is done as numbers, so `4940` and
`4940.0` match.

**Per-field reporting.** The harness reports accuracy for each of the nine
fields separately, so a failure identifies which field is weak rather than
producing a single opaque percentage.

**Absent is not null.** A key missing from a ground-truth file means "I forgot
to write this". A key set to `null` means "the document genuinely does not state
this". Treating them as the same silently converts an omission into an
assertion — and marks the model wrong for being right. The harness rejects the
former.

### The eval set

| Case | Type | Contains |
|---|---|---|
| `e01` | **Hard** | Efficacy figure, system wattage *and* LED load, warranty hours *and* rated life, luminaire *and* module flux |
| `e02` | Baseline | Single variant, every value stated once, plainly labelled |
| `e03` | Baseline | Single variant, DALI dimmable |

Baseline cases exist so that a failure can be localised. If `e02` fails, the
pipeline is broken. If only `e01` fails, the disambiguation is broken. Without
easy cases, every failure is ambiguous.

## Results

**v0 — 27/27 fields, 3/3 documents fully correct.**

All nine fields at 100%.

### The finding

`e01` contains four traps, and the model navigated all four: it took system
wattage over LED load, luminaire flux over module flux, rated life over
warranty hours, and ignored the efficacy figure entirely.

**This is not evidence that the model has lighting domain sense.** It is
evidence that *stating the domain rules explicitly in the prompt is sufficient*.
Those rules are in `extract.py`:

```
- wattage_w must be SYSTEM wattage (including driver losses).
  If the datasheet also gives LED load, do NOT use that.
- lifespan_hours must be the L80/B10 rated life. Do NOT use the
  warranty period, even if warranty hours are stated more prominently.
- Efficacy figures (lm/W) are NOT wattage and NOT flux.
```

They came from domain knowledge, not from the model.

**Planned control:** remove those three lines and re-run. The resulting drop
quantifies what the domain rules are worth in accuracy points. Until that
experiment is run, 100% is an unfalsifiable claim and is presented as such.

### Two evaluation defects found — both in the answer key

On two consecutive sessions the harness produced a wrong number because of a
defect in the ground truth rather than in the system being measured.

| Run | Reported | Actual cause |
|---|---|---|
| First | 11.1% | A formatting example had been copied in as ground truth; the model was correct on all 18 fields |
| Second | 92.6% | Two keys deleted from a ground-truth file; read as `null`, so two correct answers were marked wrong |

Both were caught within minutes because the harness runs on 3 cases rather than
waiting for 15. The comparison logic is identical at 3 or 300, so building it
early is what surfaced these while they cost minutes to fix.

**An evaluation score is only as trustworthy as the answer key behind it.** The
validation added in response to these is now part of the harness.

## Known issues

**Latency regression, unexplained.** Median latency moved from ~7 s (13 Aug) to
40.8 s (18 Aug), with one run at 176 s on a small document. Same model, same
documents. Suspected free-tier rate limiting with SDK backoff, since the eval
fires calls consecutively. Not yet investigated. The earlier cost/latency
baseline should be treated as no longer representative.

**Eval set is small.** Three documents, two of them deliberately trivial. 100%
here demonstrates that the harness works; it does not establish performance on
unseen documents.

**Adversarial coverage is thin.** One trapped document. No prompt injection
case, no non-English datasheet, no document with internally contradictory
figures.

**Eval runs are not logged.** `evaluate.py` does not call `log_run`, so eval
traffic is absent from `requests.jsonl`.

---

## What I'd do next

1. **Run the ablation** — remove the domain rules from the prompt, re-run,
   measure the drop. This is the experiment that makes the central claim
   falsifiable.
2. **Grow the eval set to 15+**, with a deliberate mix of baseline and trapped
   documents, plus adversarial cases.
3. **Investigate the latency regression** and re-establish a cost baseline.
4. **Retrieval** for datasheets too long to fit in a single prompt, measuring
   the retriever and the extractor separately so a failure can be attributed.
5. **Tracing** — per-call visibility so any past run can be reconstructed.

## Running it

```bash
git clone https://github.com/YOUR_USERNAME/clause.git
cd clause
python -m venv .venv
source .venv/bin/activate      # Windows: .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Create `.env`:

```
GOOGLE_API_KEY=your-key-here
```

```bash
python extract.py              # extract one document
python evaluate.py             # score against ground truth
uvicorn api:app --reload       # serve on http://127.0.0.1:8000/docs
```

With Docker:

```bash
docker compose up --build
```

### Adding an eval case

1. Put the datasheet text in `evals/documents/eNN.txt`
2. Copy `evals/ground_truth/_TEMPLATE.json` to `evals/ground_truth/eNN.json`
3. **Fill it in by hand from the document.** Never from a model.
4. `python evaluate.py`
